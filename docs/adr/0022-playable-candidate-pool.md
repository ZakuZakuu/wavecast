# ADR 0022: 先建可播放候选池，再让 Curator 选曲

- 状态：提议中（待评审，未实现）
- 日期：2026-10-08
- 关联：#197（选曲）、#196/PR #206（名字折叠）、#202（多样性）、#205（用户提示）、#195（总览）

## 背景

当前选曲是“LLM 凭记忆写艺人和曲名，再到曲库逐个核对”。2026-10-08 的两次本地基线暴露了这个顺序的问题：

- 主题“椎名林檎”：Agent 试过 17、ギブス、丸ノ内サディスティック、本能、歌舞伎町の女王、眩暈，曲库里都有，详情接口的 `playable` 均为 false；只有《罪と罰》可播。结果 4 首歌里 3 首是東京事変，标题却写“从她最早期的声音开始”。
- 主题“久石让为宫崎骏电影写的配乐”：艺人名字形不同被拒（#196 已处理）；LLM 写的《天空之城》与曲库标题《天空の城ラピュタ》不是同一串字，仍被拒。
- 流程里没有任何一步知道“这个艺人或主题实际有哪些歌能播”，所以不可播、叫法不同、没搜到都只能事后在窄退路里补救（目录替换池、同艺人另一首），且结果不会反映到标题、路线和主持词。

现有流程并不以艺人为中心：提案提示词要求 LLM 给出真实存在的艺人和曲名，Curator 提示词要求尽量选不同艺人，艺人只出现在退路里。本 ADR 也不引入以艺人为中心的选曲。

## 已核对的约束

- `TrackProposal`（艺人 + 曲名）只是假设，必须经确定性的曲库解析才能进入时间线（`resolution.py`）。本 ADR 不改变这条边界。
- 详情接口 `GET /tracks/{id}` 的 `playable` 是权威值，在本地观察到的网易云 sidecar 搜索结果里 `playable` 均为 false，需要详情或 playback 确认；详情与 playback 在抽查的 6 首里结论一致。
- 本地实测：搜索约 1.2 秒，详情约 2–3 秒一首。验证成本需要有上限，并发要保守，上游是匿名访问的外部服务，限流策略未知。
- 渐进路径有两处用到 Curator：`_prepare_intelligence`（首次规划）和 `_extend_underfilled_route_with_curator`（续写），候选池要同时服务两处。
- 播放和 TTS 不在此阶段，候选池只涉及曲库调用，不产生付费 provider 调用。

## 决定

### 1. 引入 `CatalogCandidatePool`，位于研究之后、Curator 之前

确定性代码构建，不由 LLM 决定：

1. **来源（围着主题，不围着艺人）：**
   - FastStart 的 `selected_next_track`/`next_candidates` 与研究包的 `candidates`（LLM 记忆中的 `TrackProposal`）；
   - 主题和研究计划里的检索词在曲库搜到的歌；
   - 仅当节目明确以某位艺人为中心（如“人物志”）时，加入该艺人的曲库检索。
2. **去重和降噪：** 按现有 `group_key`/版本信息合并同一首歌的不同版本；默认排除 live、remix、acoustic 等，除非主题要求。名字比较使用 `canonical_name`（#196）。
3. **验证可播放：** 对排序靠前的候选调用详情接口，只保留 `playable=true` 且时长有效的歌曲。验证总数、并发数和总耗时都有上限（初值：最多 24 次详情、并发 3、整体超时；数值待实验定）。
4. **池内容：** 稳定的条目 ID（即 `track_ref`）、曲库规范艺人名和曲名、时长、版本类型、来源标记。

### 2. Curator 从池里选，而不是凭记忆写

- Curator 提示词中列出池条目，要求 track-bearing chapter 的 `TrackProposal.artist/title` 必须逐字复制池条目；
- **Curator 输出契约不变**（仍是 `TrackProposal`），因此对 DeepSeek flash 的结构化输出风险最低；
- 解析阶段新增“池命中”快路径：`TrackProposal` 经 `canonical_name` 与池条目一致时，直接得到 `ResolvedTrack`（该条目已被确定性验证为可播），不再额外搜索；
- 未命中池的候选仍走现有解析路径，保持原有行为（允许发现性选曲，但会标记来源）。
- 同一艺人在一期节目里的最多首数由代码在池内/选后检查，不依赖提示词。

### 3. 多样性与种子（与 #202 联动）

- 池构建完成后，在“可替换”的候选里使用写入节目记录的随机种子做抽样排序，固定种子即可复现；
- 随机性只作用于池内排序，不改变解析和身份规则。

### 4. 失败分类与有上限的补救

每个被尝试的候选记录结构化结果：`PLAYABLE`、`UNPLAYABLE`、`NOT_FOUND`、`NAME_MISMATCH`、`PROVIDER_ERROR`。

- 池可播放数量不足以支撑目标节目时，触发**一次**补救：把“不可用清单”和已有可播放条目交给 FastStart/Curator 兜底提示，请其给出同艺人其他作品、成员/合作者、相近艺人或翻唱的候选，再按第 1 节流程验证并并入池。补救次数写死为 1，由应用代码控制，LLM 不决定是否继续。
- 分类结果和“受限艺人名单”写入节目记录，为用户提示（#205）和可观测性（#203）所用；不含音源地址。

### 5. 对账

选曲固定后，应用比较提案阶段的承诺（开场艺人、路线描述中的关键艺人）与实际曲目，把差异作为结构化“音源提示”交给前端（#205）和 Writer，不让 LLM 自由改写原因。提案阶段已展示的标题不回写（已展示的内容对听众稳定）。

### 6. 发布方式

- 引入环境开关 `WAVECAST_CATALOG_POOL`（默认关闭），逐步在本地精校环境验证后再默认开启；
- 先实现池和验证（不改变选曲行为），再接入 Curator 与解析，再加补救和字段，三步分别评审。

## 备选方案

- **放宽标题/艺人模糊匹配：** 否决。可能选中翻唱、琵琶版等不同版本，违反“不把近似匹配提升为播放身份”的约定。
- **让 LLM 同时给出别名再逐个核对：** 否决。依赖模型记忆，不稳定。
- **只靠提示词写版权规则：** 否决。flash 对长规则表遵守不稳定，硬规则放代码。
- **以艺人为中心建池：** 否决（用户顾虑）。会让同一风格总是少数艺人的少数歌曲，与多样性目标冲突；仅用于明确以艺人为中心的节目。
- **新增 Curator 输出字段 `pool_id`：** 暂不做。保持契约不变，先验证“逐字复制 + 规范化命中”是否足够；不足时再扩展。

## 影响

- 正面：不可播放和叫法不同的问题从源头减少；Curator 能看到真实可用的曲目，时长（#172）也能据此估算；失败有结构化原因。
- 成本：每个节目多出几十次曲库调用（不是付费 provider）；增加后台等待，但首曲已在播放，不挡开场。
- 风险：上游限流或变慢会拖长池构建，需要超时降级为现有流程；提示词变长；池内曲目仍可能因版权变化而失效，解析阶段依然要保留。
- 不变：生命周期、不可变已发布前缀、播放和 TTS 流程、`ResolvedTrack` 身份规则、提案生成流程（提案阶段的可播放性检查另议，见 #205）。

## 验证计划

1. 离线夹具（假 MusicProvider）：全部不可播、部分不可播、名字变体、标题别名（《天空之城》→《天空の城ラピュタ》）、超时、池不足触发补救一次且不会第二次。
2. 契约测试：Curator 输出契约不变；池命中快路径不会绕过 `playable` 检查；同一艺人首数上限。
3. 本地 live 对照（`--live --no-tts`，每次生成会产生 DeepSeek/Exa/Tavily 费用，需用户授权）：椎名林檎、久石让、一个英文爵士主题、一个游戏配乐主题，和 2026-10-08 基线（4 首、其中 3 首東京事変）对比。

## 开放问题

- 池大小、验证次数、并发、超时的取值需要在真实上游上实验后确定。
- 主题类节目（情绪、流派）没有明确艺人时，仅靠主题检索词能否搜到足够的可播候选，需要实验。
- 提案阶段是否也做一次快速可播放性检查，用于更早的用户提示（#205）。
- 渐进续写（`_extend_underfilled_route_with_curator`）使用同一个池还是为续写重新扩池，实现时按调用链确认。
