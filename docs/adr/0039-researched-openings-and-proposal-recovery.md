# ADR 0039 — 开播容错与有材料的开场

状态：Accepted，2026-10-19；仅用于新节目，实际听感待测试环境试听。

## 问题

提案请求通常只要一档，但响应契约允许 1–12 档，数量不符直接报 502（#333）。
提案选首曲时没有研究；第二首虽然有快速研究，却没有收到提案的编辑方向，
候选失败还可能用同艺人任意作品续播。已有完整开篇位置不等于材料充实：
首个间隙使用的素材通常只有泛主题检索，后面的曲目研究则更充分，造成质量落差。

## 决定

- 多返回的有效提案只取请求数量，不配音、保存或扣除多余档数。格式错误或数量不足
  合计最多补救一次。四个开场候选全部尝试；候选无法播放/未匹配时可换一组，
  与格式修复共用总计两次提案调用预算，换组及匹配另有15秒上限。
  音乐服务故障不靠重复调用模型补救；精确曲目身份和可播校验保持。
- 新建动态提案之前，复用当前研究客户端做一次轻检索：两个并行查询，共享3秒预算；
  超时保留已返回来源，取消剩余任务。无资料时继续既有路径，不伪造事实。
  最多六段来源、每段最多800字符进入同一次提案模型调用，不增加摘要或核对模型。
- 检索帮助选择切入角度和真正贴题的首曲；短导入仍完整、简短，不承担整期讲解。
  原曲可作为“相似音乐”请求的入口，不能将同艺人身份当作风格证据。
- 来源以可选的服务端 `opening_evidence` 随提案JSONB保存，经seed进入episode；
  API/分享响应排除此字段。旧记录缺失时默认为空，无数据库迁移。
- 快速选第二首同时收到原始需求、编辑方向和已有资料；新结果与既有证据合并。
  `FastStartPlan.allow_artist_fallback` 默认false，只有明确适合宽泛主题时才允许
  同艺人曲库兜底；否则交给后续正式策划，不提交离题歌曲。
- 两首可播后、第一首播放期间，复用既有短检索研究实际曲目对，随后走现有
  material/Writer/TTS链路。开篇仍优先于全期策划，75秒等原有电台预算保持。
  新资料合并保存，锁定前两首后恢复正式策划时也继续携带，不再丢弃为无资料上下文。

用户明确接受为首曲质量增加少量有上限的等待，修订ADR0016“不在提案做检索”这一限制。
不提前研究/配音整期、不改变已发布音频、不增加模型复审、前端状态或播放阻塞。
资料来源是证据，简介是意图；日期、人物状态及已有配音语言保护继续保留。

## 验证

离线验证多返回/少返回、格式与选曲共享修复预算、服务故障不重试、第四候选、
检索超时及取消清理、资料持久化与公开响应隔离、快速策划与正式策划沿用资料、
同艺人兜底许可。数据库重建/重复保存由Postgres集成用例验证。

真实小测只运行检索/提案，不默认生成完整节目。最终验收记录首响、首段完整口播
准备时间与选曲/衔接；文笔和真实TTS不能由结构测试替代。网络、曲库及外部模型仍可能失败，
3秒是研究预算，不是整体开播时长承诺。
